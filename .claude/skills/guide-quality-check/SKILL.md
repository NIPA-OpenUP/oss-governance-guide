# Guide Quality Check — 검증 방법

개정 원고를 두 층위에서 검증한다. **기계적 정합성**(스크립트로 결정적으로 판정)과 **사실 정확성**(적대적 검증으로 판정)은 실패 방식이 다르므로 방법도 다르다.

| 층위 | 실패 방식 | 검증 방법 |
|------|----------|----------|
| 기계적 정합성 | 빌드 실패 또는 렌더링 깨짐 — 즉시 드러난다 | 번들 스크립트로 전수 검사 |
| 사실 정확성 | 조용히 통과해 출간된다 | 주장별 독립 반박 시도 |

사실 오류가 더 위험하다. 빌드는 깨지면 고치지만, 잘못된 규제 시행일은 기업의 잘못된 판단으로 이어진다.

## 1. 기계적 정합성 — 스크립트 전수 검사

같은 검사를 손으로 만들지 않는다. 정적 검사는 결정적이므로 스크립트가 정확하고 빠르다.

```bash
# content/en 아래 전체 검사
python3 .claude/skills/guide-quality-check/scripts/check_guide_integrity.py

# 특정 파일만
python3 .claude/skills/guide-quality-check/scripts/check_guide_integrity.py content/en/using/_index.md

# 후속 단계가 프로그래밍으로 소비할 때
python3 .claude/skills/guide-quality-check/scripts/check_guide_integrity.py --json

# _workspace/ 초안 검사 — 초안은 페이지 번들 밖이므로 이미지 조회 위치를 지정한다
python3 .claude/skills/guide-quality-check/scripts/check_guide_integrity.py \
  _workspace/06_edited_using.md --bundle content/en/using
```

종료 코드: `0` = blocking 없음, `1` = blocking 있음, `2` = 입력 오류.

검사 항목과 심각도:

| 항목 | 심각도 | 왜 그 심각도인가 |
|------|--------|----------------|
| `front_matter` 필수 필드 누락 | blocking | `title` 없으면 페이지 제목이 비고, `weight` 없으면 사이드바 순서가 불안정해진다 |
| `undefined_footnote` | blocking | 본문에 `[^label]`이 원문 그대로 노출된다 |
| `dead_anchor` | blocking | 링크가 아무 곳으로도 가지 않는다. 한글 헤딩을 앵커로 쓰므로 헤딩 수정 시 조용히 발생한다 |
| `missing_image` | blocking | `imgproc`는 페이지 리소스만 처리하므로 파일이 없으면 빌드가 실패한다 |
| `shortcode` 불균형 | blocking | 빌드 실패 |
| `unknown_shortcode` | blocking | Docsy가 제공하지 않는 shortcode는 빌드 실패 |
| `table` 열 수 불일치 | blocking | 표가 문단으로 렌더링된다 |
| `unused_footnote_def` | warn | 렌더링에 영향 없음. 개정 중 문장을 지우고 정의를 남긴 흔적 |
| `footnote` 정의 중복 | warn | Hugo가 첫 정의를 쓴다. 의도한 출처가 표시되지 않을 수 있어 확인 대상 |
| `duplicate_heading` | warn | 두 번째 헤딩 슬러그에 `-1`이 붙어 앵커가 예상과 달라진다 |

`--bundle`을 빠뜨리고 초안을 검사하면 `missing_image`가 대량 발생한다. 순서 문제를 원고 결함으로 보고하지 않는다.

## 2. 빌드 확인

로컬에 `hugo`가 없을 수 있다. **없으면 정적 검사만 하고 그 사실을 보고한다** — 빌드하지 않고 "빌드 통과"로 보고하는 것이 이 검증의 최악의 실패다.

```bash
hugo version            # 없으면 여기서 멈추고 정적 검사 결과만 보고
hugo --renderToMemory   # 파일을 쓰지 않는 빠른 검증
```

CI 기준은 Hugo extended 0.78.2다. `hugo --minify`는 `node_modules`(autoprefixer)를 요구하므로 검증 목적으로는 불필요하다 — node_modules가 없어 실패한 빌드는 **원고 결함이 아니라 환경 문제**이므로 구분해 보고한다.

빌드 에러 해석:

| 메시지 | 원인 |
|--------|------|
| `failed to extract shortcode` | 없는 shortcode 또는 닫는 태그 누락 |
| `resource not found` | imgproc 대상 이미지가 페이지 번들에 없음 |
| `unmarshal failed` | front matter YAML 문법 오류 |

`themes/docsy/` 아래 파일이 변경되어 있으면 개정 작업의 부작용이다. 테마는 vendored 상태로 커밋되어 있어 수정이 조용히 추적되므로 확인해 보고한다.

```bash
git status --porcelain themes/docsy | head
```

## 3. 사실 정확성 — 적대적 검증

**주장을 승인하려 하지 말고 무너뜨리려 한다.** 검증자의 목표가 통과 판정이면 표면 확인에서 멈추고, 목표가 반박이면 실질 확인까지 간다.

### 판정 원칙

- **불확실하면 반박 쪽으로 기운다.** 통과시킨 오류의 비용이 반박한 정상 서술의 비용보다 훨씬 크다. 애매하면 `refuted: true` + 낮은 심각도로 보고해 집필자가 확인하게 한다.
- **표면 일치와 실질 지지를 구분한다.** URL이 열리고 보고서명이 맞아도, 그 보고서가 말한 것이 주장과 다르면 반박이다.
- **독립적으로 판정한다.** 다른 검증자의 판정을 참고하지 않는다. 합의가 아니라 독립 판정이 신호를 만든다.
- **재현 가능하게 쓴다.** "출처가 부실하다"가 아니라 "URL은 열리지만 해당 페이지에 53%라는 수치가 없다. 페이지의 관련 수치는 47%(2026년판)이다"로 쓴다.

### 반박 유형과 심각도

| 유형 | 무엇인가 | 심각도 |
|------|---------|--------|
| `wrong_number` | 수치가 원문과 다름 | critical |
| `wrong_scope` | 모수가 바뀜 — "감사된 코드베이스의 53%"를 "기업의 53%"로 | critical |
| `misquoted_clause` | 라이선스·규제 조항 인용이 원문과 의미가 다름 | critical |
| `stale_timing` | 2026년 7월 기준 이미 시행된 것을 "예정"으로, 지난 예측을 미래로 | critical |
| `content_mismatch` | URL은 살아 있으나 해당 내용이 없음 | major |
| `no_source` | 각주 없이 단정된 사실 서술 | major |
| `overstated` | 근거보다 강한 결론 — 상관을 인과로, 일부를 전체로 | major |
| `dead_link` | URL 접근 불가 | minor |

### 반박하지 않는 것

- **규범적 서술** — "~하는 것이 바람직하다", "~를 권장한다"는 사실 검증 대상이 아니다. 의견을 사실처럼 반박하면 검증 신호가 오염된다.
- **네트워크 실패를 죽은 링크로 단정** — 재시도 1회 후에도 실패하면 `severity: "minor"` + "네트워크 확인 실패, 사람 확인 필요"로 기록한다. 살아 있는 링크를 죽었다고 보고하면 불필요한 교체가 발생한다.
- **유료 장벽 뒤의 출처** — 공개 요약으로 교차 확인하고, 불가하면 `minor`로 보고한다.

### 검증 대상 추출

원고에서 검증할 주장을 뽑는 기준. 전부 검증하면 비용이 과하고, 임의로 고르면 위험한 것이 빠진다.

**반드시 검증한다:**
- 숫자·비율·연도가 포함된 문장
- 규제·표준의 시행 시기와 적용 대상
- 라이선스 조항 인용
- 각주가 붙은 모든 문장 (각주가 실제로 그 문장을 지지하는지)
- 각주 없이 단정된 사실 서술

**검증하지 않는다:**
- 개념 정의, 절차 설명, 권고 서술
- 이전 판에서 검증되었고 개정에서 손대지 않은 문단

```bash
# 수치가 있는 문장 추출 — 검증 대상 후보
grep -nE '[0-9]+(\.[0-9]+)?%|[0-9]{4}년|[0-9]+배' _workspace/06_edited_using.md

# 각주 붙은 문장
grep -nE '\[\^[^]]+\][^:]' _workspace/06_edited_using.md
```

## 4. 검증 순서

순서를 지키는 이유가 있다.

1. **기계적 검사 먼저** — blocking이 있으면 그 원고는 아직 검증 대상이 아니다. 깨진 마크업 위에서 사실 검증을 하면 재작업이 두 번 발생한다.
2. **사실 검증** — 주장별 독립 병렬. 삽화 생성과 동시에 진행 가능하다(서로 의존하지 않는다).
3. **이미지 배치 후 기계적 재검사** — `missing_image`는 이미지가 생성된 다음에만 의미 있게 판정된다.
4. **빌드 확인** — 마지막. 앞 단계를 통과하지 못한 원고를 빌드하는 것은 낭비다.

## 5. 판정 종합

`verdict: "pass"`는 다음 셋을 모두 만족할 때만 부여한다.

- 기계적 검사의 blocking이 0건
- critical 반박이 0건
- 빌드가 시도되었고 exit 0 (빌드 불가 환경이면 그 사실을 명시하고 판정을 유보)

major 반박이 남아 있으면 `needs_revision`이다. minor는 출간 후 보완 가능하지만 목록으로 남긴다.

**커버리지를 침묵으로 절단하지 않는다.** 검증 대상 중 일부만 확인했으면 확인한 수와 전체 수를 함께 보고한다. "검증 완료"는 전수 확인을 뜻하므로, 표본 검증을 완료로 보고하면 다음 사람이 검증된 원고로 오해한다.

## 안티패턴

- **스크립트로 되는 검사를 손으로 반복** — 느리고 누락된다.
- **빌드하지 않고 빌드 통과로 보고** — 가장 위험한 허위 보고.
- **환경 문제(node_modules 없음)를 원고 결함으로 보고** — 잘못된 재작업을 유발한다.
- **`--bundle` 없이 초안 검사** — `missing_image` 대량 오탐.
- **네트워크 실패를 죽은 링크로 단정** — 살아 있는 출처를 교체하게 만든다.
- **규범적 서술을 사실로 반박** — 검증 신호가 오염된다.
- **다른 검증자 판정 참고** — 적대적 검증의 독립성이 깨진다.
- **표본 검증을 완료로 보고** — 검증되지 않은 원고가 검증된 것으로 통과한다.
