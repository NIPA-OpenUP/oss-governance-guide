# Published Edition Baseline — 발간본 대조와 기준선 확정

개정 작업의 첫 관문이다. **잘못된 원본 위에서 감사·집필하면 이후 전부가 낭비된다.**

이 저장소에는 두 갈래 원고가 있다.

| 원고 | 상태 | 형태 |
|------|------|------|
| `content/en/*/_index.md` | 마지막 갱신 2024-11 | Hugo 마크다운, 각주 `[^label]`, "오픈소스" |
| `[2025] ...가이드.pdf` | 2025-02 발간, 180쪽 | 조판 PDF, 각주 페이지 하단 `*`, "오픈소스SW" |

발간본이 저장소보다 **날짜가 늦지만 자동으로 최신은 아니다.** 발간은 특정 시점의 저장소를 편집·조판한 결과이고, 그 이후 저장소가 다시 갱신되었을 수 있다. 판정은 날짜가 아니라 **내용**으로 한다.

## 1. 추출

```bash
python3 .claude/skills/published-edition-baseline/scripts/extract_published_pdf.py \
  '[2025] 기업 오픈소스SW 거너번스 가이드.pdf' \
  -o _workspace/00_published_2025.md --report
```

스크립트가 하는 일:
- `pdftotext -layout`으로 추출 (없으면 `pypdf` 폴백)
- 여러 페이지에 반복되는 짧은 줄을 머리말/꼬리말로 보고 제거 (`--report`로 무엇을 지웠는지 확인)
- 쪽번호만 있는 줄 제거
- 조판 폭에 맞춰 끊긴 줄을 문단으로 병합 — **한국어 종결어미(`~다.`)를 문단 경계로 쓴다**
- `-`나 `/`에서 접힌 URL 복원 (각주 URL이 통째로 죽는 것을 막는다)
- 페이지 경계를 `<!-- page:N -->`로 보존

`<!-- page:N -->` 주석을 지우지 않는다. 대조 결과에서 "발간본 42쪽"처럼 위치를 특정해야 사람이 원본을 확인할 수 있다.

표·도표가 많은 구간에서 병합 결과가 이상하면 `--keep-linebreaks`로 원형을 확인한다. 머리말 제거가 본문을 지웠다고 의심되면 `--min-repeat`를 올린다(기본 5).

## 2. 정규화 — 비교 전에 노이즈를 없앤다

추출 텍스트를 그대로 비교하면 **차이의 대부분이 조판·편집 흔적**이라 실제 내용 차이가 묻힌다. 비교 전에 양쪽을 같은 기준으로 정규화한다.

| 노이즈 | 정규화 |
|--------|--------|
| 용어 일괄 치환 ("오픈소스" ↔ "오픈소스SW") | 치환 규칙을 먼저 찾아 한쪽으로 통일한 뒤 비교 |
| 각주 표기 (`[^label]` vs 하단 `*`) | 표기를 버리고 **각주의 내용과 URL만** 비교 |
| 따옴표 모양 (`"` vs `“”`), 공백, 줄바꿈 | 통일 |
| Hugo shortcode (`{{< imgproc >}}`, `{{% alert %}}`) | 저장소 쪽에서 제거 — 발간본에는 대응물이 없다 |
| front matter | 저장소 쪽에서 제거 |
| 표 마크다운 (`\|---\|`) | 셀 내용만 남기고 구분선 제거 |

**용어 치환 규칙을 먼저 찾는다.** 규칙을 모르고 비교하면 전 문단이 "다름"으로 나온다.

```bash
# 발간본이 쓰는 표기 빈도
grep -o '오픈소스SW' _workspace/00_published_2025.md | wc -l
grep -oE '오픈소스(?!SW)' _workspace/00_published_2025.md | wc -l
# 저장소 쪽
grep -o '오픈소스SW' content/en/*/_index.md | wc -l
```

치환은 **편집 결정이지 내용 갱신이 아니다.** `editorial_substitutions`로 따로 기록하고 내용 차이와 섞지 않는다.

## 3. 장·절 대응

발간본은 로마숫자 장 체계, 저장소는 디렉토리 slug다. 1:1이 아닐 수 있다.

| 발간본 (머리말에서 확인됨) | 저장소 slug |
|---|---|
| 서문 / 배경과 취지 | `intro` |
| I. 오픈소스SW 사용하기 | `using` |
| II. 오픈소스SW 기여하기 | `contributing` |
| III. 오픈소스SW 공개하기 | `releasing` |
| IV. OSPO | `ospo` |

이 표는 출발점이며 확정이 아니다. 실제 목차를 추출해 확인한다:

```bash
grep -nE '^(I{1,3}V?|IV|V)\. |^[0-9]+\. |^제 ?[0-9]+ ?[장절]' _workspace/00_published_2025.md | head -40
```

대응이 확정되지 않는 장은 **억지로 매핑하지 않는다.** `unmapped`에 남기면 사람이 판단하지만, 잘못 매핑하면 엉뚱한 병합이 조용히 일어난다.

## 4. 판정 — 섹션별 기준 소스

절 단위로 비교하고 섹션 단위로 판정한다. 문단 단위는 조판 노이즈가 크고, 장 단위는 차이 위치를 특정할 수 없다.

| 판정 | 조건 |
|------|------|
| `repo` | 저장소가 발간 이후 갱신됨. 발간본에만 있는 내용이 없거나 사소함 |
| `published` | 발간 과정에서 내용이 추가·수정되었고 저장소에 반영되지 않음 |
| `merge` | 발간본의 편집 개선과 저장소의 내용 추가가 서로 다른 절에 있음 |

**불확실하면 `merge`로 기울인다.** 한쪽을 버리면 그 내용은 개정판에서 사라지지만, 병합하면 후속 집필·비평 단계에서 중복을 정리할 기회가 남는다. 되돌릴 수 있는 실수를 택한다.

판정에는 반드시 근거를 붙인다. "발간본이 더 최신"은 근거가 아니다 — "발간본 42쪽에 CRA 시행 일정 표가 있으나 저장소 using 절에는 없다"가 근거다.

## 5. 판정하지 않는 것

- **어느 쪽 문장이 더 좋은가** — 문체 판단은 교정 단계의 몫이다. 여기서는 내용의 유무와 최신성만 본다.
- **발간본에만 있는 내용을 개정판에 넣을지** — `worth_keeping`으로 의견을 남기되, 결정은 개정 계획과 사용자 승인의 몫이다. 2026년 기준으로 이미 낡은 내용이면 발간본에 있어도 넣지 않는 것이 맞다.
- **용어 최종 표기** — `editorial_substitutions`로 후보를 제시하고 결정은 승인 게이트로 넘긴다. "오픈소스SW"는 NIPA 발간물 표기 관례일 수 있어 저장소 표기와 다른 이유가 있다.

## 안티패턴

- **날짜로 최신성 판정** — 발간일이 늦다고 모든 절이 최신인 것은 아니다.
- **정규화 없이 diff** — 차이의 대부분이 조판 흔적으로 나와 실제 차이가 묻힌다.
- **용어 치환을 내용 변경으로 계수** — 전 문단이 "다름"이 되어 판정이 불가능해진다.
- **추출 실패를 "발간본에 내용 없음"으로 처리** — 발간본의 갱신분이 통째로 유실된다. 추출 실패는 실패로 보고하고 저장소 기준으로 진행한다.
- **`<!-- page:N -->` 제거** — 사람이 원본을 확인할 경로가 사라진다.
- **대응 안 되는 장을 억지 매핑** — 엉뚱한 병합이 조용히 일어난다.
- **한쪽을 통째로 선택** — 편한 판정이지 정확한 판정이 아니다.

## 번들 스크립트

`scripts/extract_published_pdf.py` — PDF 본문 추출·정규화. `--report`로 제거한 머리말 목록 확인, `--pages`로 범위 지정, `--keep-linebreaks`로 병합 전 원형 확인.
