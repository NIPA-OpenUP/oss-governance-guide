# 2026 개정판 필수 확인 주제 체크리스트

조사 **종료 전에** 자신의 축 항목을 전수 대조한다. 체크리스트에 있으나 확인하지 못한 항목은 발견 목록에 `confidence: "low"` + 미확인 사유로 남긴다 — 조용히 빠뜨리면 완전성 검토 단계에서 늦게 발견되어 재작업이 커진다.

이 목록은 "2026년 기업 오픈소스 거버넌스 문서라면 독자가 찾을 것"을 기준으로 만들었다. 조사 결과 해당 주제가 실제로는 중요하지 않다고 판단되면 그 판단을 근거와 함께 기록한다 — 판단 없이 생략하는 것과 근거 있게 제외하는 것은 다르다.

## regulation

- [ ] **EU Cyber Resilience Act** — 단계별 발효 일정(보고 의무 시점과 전면 적용 시점을 구분), 오픈소스 스튜어드(open source steward) 개념과 재단·개인 관리자의 지위, 국내 기업 중 적용 대상 조건, 제조사의 SBOM·취약점 처리 의무
- [ ] **EU AI Act** — 오픈소스 예외의 실제 범위와 예외가 적용되지 않는 경우, 범용 AI 모델 제공자 의무, 단계별 시행 일정
- [ ] **미국 SBOM 정책** — 행정명령 이후 실제 조달 요건화 진행 상태, CISA 최소 요구 사항의 갱신, FDA 의료기기 요건
- [ ] **ISO/IEC 5230** — 현행 판번호와 개정 여부, 인증 취득 절차와 국내 취득 기업 현황
- [ ] **ISO/IEC 18974** — 보안 보증 표준의 위상과 5230과의 관계
- [ ] **SPDX / CycloneDX 표준화 상태** — SPDX 3.x의 변화(프로필 구조), CycloneDX의 표준 지위, 두 포맷의 상호 변환 실무
- [ ] **국내 SW공급망 보안 정책** — 소프트웨어진흥법 관련 조항, 공공 조달의 SBOM 요구 도입 상태, 산업별 정책(의료·국방·제조) 진행 상태
- [ ] **제조물책임(PLD) 개정과 소프트웨어** — 소프트웨어가 제조물에 포함되면서 생기는 오픈소스 사용 기업의 책임 변화
- [ ] **라이선스 변경 흐름** — 주요 프로젝트의 비오픈소스 라이선스 전환(BSL/SSPL 등)과 그에 따른 포크, 기업이 취할 대응 절차

## security

- [ ] **SLSA** — 현행 버전의 레벨 정의, 레벨별 요구사항, 국내 기업의 현실적 도달 경로
- [ ] **Sigstore / cosign** — 실제 도입 수준, 서명 검증을 CI에 넣는 방법
- [ ] **OpenSSF Scorecard** — 의존성 선택 기준으로 쓰는 방법, 점수의 한계
- [ ] **VEX / OpenVEX** — SBOM만으로는 대응이 불가한 이유, VEX 생성·소비 실무, 오탐 감소 효과
- [ ] **OSV / OSV-Scanner** — NVD 지연 문제와 대안 데이터 소스, 스캐너 조합
- [ ] **EPSS / KEV** — CVSS 점수만으로 우선순위를 정하는 관행의 한계와 개선
- [ ] **최근 공급망 공격 사고** — 근본 원인 유형별로(빌드 시스템 침해, 계정 탈취, 유지관리자 소셜 엔지니어링, 타이포스쿼팅, 의존성 혼동) 각 1건 이상. 기업이 취할 방어 조치까지
- [ ] **유지관리자 지속가능성** — 단일 유지관리자 의존 리스크, 기업의 후원·기여 전략과 연결
- [ ] **AI 생성 코드의 보안** — 생성 코드의 취약점 유입 경로와 검증 절차
- [ ] **국내 하위 공급망 관리** — SI·수급 구조에서 SBOM 요구를 관철하는 계약·검증 방법

## ai

- [ ] **OSAID** — 현행 판번호, 정의의 3요소(데이터 정보·코드·가중치), 승인/미승인 사례, 정의를 둘러싼 주요 비판
- [ ] **"오픈 웨이트" vs "오픈소스"** — 용어 구분의 실무적 중요성, 기업이 사내 문서에서 어떻게 표기해야 하는가
- [ ] **주요 모델 라이선스 조항** — 대표 모델군의 커스텀 라이선스에서 사용 제한·사용자 수 임계·재배포 조건·상표 조항. **원문 인용 필수**
- [ ] **파생 모델의 의무** — 파인튜닝 결과물의 라이선스 승계, 모델 병합 시 라이선스 충돌
- [ ] **데이터셋 라이선스** — 모델 라이선스와 분리되는 구조, 데이터셋 출처 불명 리스크
- [ ] **생성형 AI 코딩 도구의 라이선스 리스크** — 학습 데이터 유래 코드 혼입 가능성, 저작권 귀속 논의 상태, 탐지 도구, 기업 내부 정책에 넣어야 할 항목
- [ ] **AI BOM / ML-BOM** — SPDX 3.x AI 프로필, CycloneDX ML-BOM, 무엇을 기록해야 하는가
- [ ] **사내 AI 코딩 도구 정책 템플릿** — 실용 산출물. 허용 범위, 검증 절차, 금지 사항, 기록 의무
- [ ] **AI 모델을 제품에 포함할 때의 고지 의무** — 기존 오픈소스 고지 프로세스에 모델을 어떻게 편입하는가

## market

- [ ] 기존 원고가 인용한 **모든 연례 보고서의 최신판** — 원고에서 보고서명을 전수 추출해 대조 (누락 없는 확인이 이 축의 핵심 임무)
- [ ] **3개 연도 추세** — 단일 연도 수치보다 추세가 유용하다. 주요 지표는 과거판 수치를 함께 확보
- [ ] **국내 오픈소스 시장 규모·도입률** — NIPA·SPRi 등 국내 통계의 최신판
- [ ] **OSPO 도입률** — TODO Group 설문 최신판, 국내 기업 OSPO 현황
- [ ] **국내 기업 거버넌스 사례** — 공개 확인 가능한 것 위주로 최소 4~5건. 기존 원고의 집필사(카카오·라인·SK텔레콤) 외 기업도 포함
- [ ] **해외 기업 사례** — 기존 원고 언급 기업들의 현재 상태 확인(조직 변화, 정책 변경)
- [ ] **재단·커뮤니티 프로그램** — OpenSSF·OpenChain·TODO Group의 현행 프로그램과 국내 참여 경로
- [ ] **AI 시대의 오픈소스 기여 변화** — 기여량·기여 방식 변화에 관한 통계가 있는지

## tooling

- [ ] 원고 등재 **모든 도구의 생존 확인** — 아카이브·인수·리브랜딩·라이선스 변경. 전수 확인이 이 축의 핵심 임무
- [ ] **로고 갱신 필요 목록** — 제품명이 바뀐 도구의 로고 이미지
- [ ] **SBOM 생성·소비 도구** — Syft, Trivy, cdxgen 등 신규 등재 후보
- [ ] **SBOM 관리 플랫폼** — Dependency-Track 등, SBOM을 만든 다음 무엇으로 관리하는가
- [ ] **국내 도구 현황** — FOSSLight의 현행 구성, 국내 상용 도구
- [ ] **도구 선택 기준표** — 실용 산출물. 조직 규모·개발 언어·배포 형태별 선택 가이드
- [ ] **CI 통합 방법** — 도구를 개발 프로세스에 붙이는 구체적 지점(PR 검사, 릴리스 게이트)
- [ ] **AI/모델 자산을 다루는 도구** — 모델·데이터셋의 라이선스를 스캔하는 도구가 존재하는가

## 기존 원고 갱신 대상

모든 축이 공통으로 확인한다. 원고에서 다음 패턴을 기계적으로 추출해 대조한다.

```bash
grep -nE '20(1[0-9]|2[0-5])년' content/en/*/_index.md      # 지나간 연도 서술
grep -nE '최근|현재|향후|예정|전망|올해' content/en/*/_index.md   # 상대 시점 표현
grep -nE '^\[\^[^]]+\]:' content/en/*/_index.md             # 각주 출처 생존 확인
grep -noE '\{\{< imgproc [a-zA-Z0-9_-]+' content/en/*/_index.md  # 이미지 참조
```

- [ ] 지나간 연도가 박힌 서술 전수 확인
- [ ] "2024년 현재" 류 표현 전수 갱신 대상 표시
- [ ] 각주 URL 전수 생존 확인
- [ ] 이미 지나간 예측·전망 서술 확인 ("향후 2년간 ~할 것으로 전망")
- [ ] 원고의 도구 로고 이미지가 현재 브랜드와 일치하는지
