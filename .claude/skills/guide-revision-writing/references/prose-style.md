# 문체 규약 상세

SKILL.md의 보충. 집필 시 문장 판단이 애매할 때, 교정 시 판정 기준이 필요할 때 읽는다.

이 가이드의 문장 목표는 **독자가 한 번에 처리해야 하는 생각의 수를 줄이는 것**이다. 문장을 아름답게 만드는 것이 아니다. 기업 담당자가 업무 중에 읽고 바로 판단할 수 있어야 한다.

## 1. 문말 어미

**'~한다' 평서문 문어체.** 기존 원고 전체가 이 어미를 쓰며, 어미가 섞이면 문서가 여러 사람의 조각처럼 읽힌다.

| 쓴다 | 쓰지 않는다 |
|------|-----------|
| ~한다 / ~이다 / ~된다 | ~합니다 / ~입니다 (존댓말) |
| ~해야 한다 | ~해야 합니다 / ~하세요 |
| ~할 수 있다 | ~할 수 있어요 |
| ~하는 것이 바람직하다 | ~하는 게 좋다 (구어체) |

1인칭 복수("우리는", "우리가")는 쓰지 않는다. 예외로 "이 가이드에서는", "본 장에서는"은 기존 원고의 관례이므로 허용한다.

수사적 질문과 감탄은 쓰지 않는다. 단, 도입부에서 주제를 여는 질문 하나는 기존 원고에도 있으므로(예: "이러한 성장과 변화의 근간은 무엇일까?") 장 도입에 한해 허용한다. 본문 중간에 쓰면 밀도가 흐트러진다.

## 2. 추상명사 해체

한국어 기술 문서가 안 읽히는 가장 큰 원인은 명사를 쌓는 것이다. 동사로 풀면 주체와 행동이 드러난다.

| 고치기 전 | 고친 후 |
|----------|--------|
| 오픈소스 라이선스 의무사항의 준수 여부에 대한 검토의 수행 | 오픈소스 라이선스 의무를 지켰는지 검토한다 |
| 컴플라이언스 프로세스의 정립을 통한 리스크의 최소화 | 컴플라이언스 프로세스를 세워 리스크를 줄인다 |
| SBOM 생성의 자동화 적용 | SBOM을 자동으로 생성한다 |
| 취약점에 대한 대응 체계의 구축이 요구된다 | 취약점에 대응할 체계를 갖춰야 한다 |

판정 기준: **한 문장에 '~의 ~의'가 두 번 이상 나오거나, '~함/~됨/~화/~성' 명사가 세 개 이상 겹치면** 해체 대상이다.

'~에 대한'은 대부분 삭제하거나 조사로 바꿀 수 있다. "라이선스에 대한 검토" → "라이선스 검토".

## 3. 번역투 목록

영어 문헌을 참조해 쓴 기술 문서에 반복적으로 들어오는 패턴.

| 번역투 | 고친 후 | 왜 |
|--------|--------|-----|
| ~할 필요가 있다 | ~해야 한다 | need to의 직역. 의무의 강도가 흐려진다 |
| ~하는 것이 가능하다 | ~할 수 있다 | it is possible to의 직역 |
| ~에 의해 ~되어진다 | ~가 ~한다 (능동) | 이중 수동. 행위 주체가 사라진다 |
| ~를 갖는다 | ~가 있다 / ~를 포함한다 | have의 직역 |
| ~에 있어서 | ~에서 / ~의 경우 | in의 직역 |
| ~로부터 | ~에서 | from의 직역 (물리적 출처가 아니면) |
| 다양한 ~들 | 여러 ~ / ~ (복수 표지 생략) | 한국어는 복수 표지를 남용하지 않는다 |
| ~와 같은 것들 | ~ 등 | such as의 직역 |
| 보다 나은 / 보다 효율적인 | 더 나은 / 더 효율적인 | 비교 대상 없는 '보다'는 일본어투 |
| 중요한 역할을 한다 | (무엇을 하는지 구체적으로) | plays an important role의 직역. 정보가 없다 |

**수동태 판정:** 행위 주체를 밝힐 수 있으면 능동으로 쓴다. 밝힐 수 없거나 주체가 중요하지 않을 때만 수동을 쓴다. "SBOM이 생성된다"보다 "도구가 SBOM을 생성한다"가 낫고, 누가 생성하는지가 문맥에서 자명하면 "SBOM을 생성한다"로 주어를 생략한다.

## 4. 사실과 해석의 분리

이 가이드에서 특히 중요하다. 독자가 "이건 조사 결과인가, 필자의 권고인가"를 구분해야 자사 상황에 적용할 수 있다.

**뭉친 문장:**
> 감사된 코드베이스의 절반 이상이 라이선스 충돌을 포함하므로 모든 기업은 자동화 스캐닝 도구를 도입해야 한다.

**분리한 문장:**
> 2026년 조사에 따르면 감사된 코드베이스의 절반 이상이 라이선스 충돌을 포함한다[^ref]. 수동 검토로는 이 규모를 다루기 어렵기 때문에, 자동화 스캐닝 도구 도입을 권장한다.

분리하면 (a) 사실에는 각주가 붙고, (b) 권고에는 이유가 붙는다. 뭉친 문장은 둘 다 없어도 그럴듯하게 읽히기 때문에 검증을 빠져나간다.

**인과의 중간 단계를 복원한다.** "A이므로 B다"에서 A와 B 사이에 생략된 단계가 있으면 채운다. 위 예에서 "수동 검토로는 이 규모를 다루기 어렵다"가 복원된 중간 단계다.

## 5. 문단 하나에 역할 하나

문단마다 역할을 하나만 준다. 역할이 섞이면 독자가 어디까지가 배경이고 어디부터가 지침인지 놓친다.

| 역할 | 문단이 하는 일 |
|------|--------------|
| 배경 | 왜 이 주제가 문제인가 |
| 정의 | 용어·개념이 무엇인가 |
| 사실 | 조사·통계·규제 내용 (각주 필수) |
| 판단 | 그래서 무엇을 권고하는가 |
| 절차 | 무엇을 어떤 순서로 하는가 (목록·표로 전환 고려) |

한 문단이 5문장을 넘으면 역할이 섞였는지 확인한다. 절차 역할의 문단은 대부분 목록이나 표로 바꾸는 것이 낫다 — 산문으로 된 절차는 독자가 자기 진행 위치를 잃는다.

## 6. 용어 표기 통일

섹션마다 표기가 달라지면 같은 개념인지 독자가 확신할 수 없다. 개정 시 아래 기준으로 통일하고, 결정 사항을 `_workspace/`의 용어 결정 기록에 남겨 다음 섹션이 따르게 한다.

| 개념 | 표기 | 쓰지 않음 |
|------|------|----------|
| 오픈소스 | **오픈소스** | 공개 소프트웨어, 오픈 소스(띄어쓰기), OSS(본문) |
| 오픈소스 프로그램 사무국 | 첫 등장 `OSPO<sub>Open Source Program Office</sub>`, 이후 `OSPO` | 오픈소스 사무국과 혼용 |
| 소프트웨어 명세서 | 첫 등장 `SBOM<sub>Software Bill of Materials</sub>`, 이후 `SBOM` | 소프트웨어 자재명세서와 혼용 |
| 컴플라이언스 | **컴플라이언스** | 준법, 규정 준수(혼용) |
| 취약점 | **보안 취약점** 또는 **취약점** (장 안에서 일관되게) | 결함, 버그 |
| 기여 | **기여** | 컨트리뷰션 |
| 공개 | **공개** (오픈소스로 배포하는 행위) | 릴리즈, 오픈 |

**약어 규칙:** 영문 약어는 첫 등장에서만 풀어 쓴다. 각 섹션은 독립적으로 읽히므로 **섹션마다 첫 등장에서 다시 풀어 쓴다**.

**고유명사는 원 표기를 따른다.** 제품·조직명을 한글로 음차하지 않는다(`Black Duck`, `Linux Foundation`). 제품명이 바뀐 경우 "Mend(구 WhiteSource)"처럼 병기한다.

## 7. 교정하지 않는 것

교정 단계에서 손대면 사고가 나는 것들.

- **수치·연도·비율** — 문장을 다듬다가 "53%"를 "절반 이상"으로 바꾸면 검증 통과한 정확한 서술이 부정확해진다.
- **고유명사·라이선스명·조항 인용** — 원문 표기를 유지한다.
- **헤딩 텍스트** — 앵커 링크가 깨진다. 헤딩 수정은 집필 단계의 결정이다.
- **마크업** — front matter, `{{< imgproc >}}`, `{{% alert %}}`, 표 문법, 각주 정의, 내부 앵커 링크.
- **인용문 내부** — 인용은 원문 그대로 둔다. 용어 통일 규칙도 인용 내부에는 적용하지 않는다.
- **사실 오류** — 발견하면 표시만 하고 고치지 않는다. 사실 판정은 검증 단계의 역할이며, 교정자가 사실을 고치면 근거 없는 수정이 원고에 들어간다.
- **저자의 목소리** — 문장을 매끄럽게 만드는 것과 표준화된 무색 문장으로 바꾸는 것은 다르다. 이 가이드는 국내 실무자 네 명이 쓴 문서이고, 그 흔적이 남아 있는 것이 정상이다.
