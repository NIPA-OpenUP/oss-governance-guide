# Guide Revision Writing — 섹션 집필·개정 규약

「기업 오픈소스 거버넌스 가이드」의 본문을 쓰는 규약. 이 가이드는 Hugo + Docsy로 빌드되는 한국어 기술 문서이며, 마크업 규약 위반은 빌드 실패나 렌더링 깨짐으로 직결된다.

**집필 전에 담당 섹션의 인접 문단을 읽는다.** 이 문서는 네 명의 실무자가 이어 쓴 원고이고, 개정판이 기존 문체·밀도와 어긋나면 독자가 이질감을 느낀다. 규약보다 인접 문단이 정확한 기준이다.

## 절대 어기지 않는 3가지

이 셋은 어기면 조용히 깨지고 나중에 발견된다.

1. **헤딩 텍스트를 임의로 바꾸지 않는다.** 원고는 한글 헤딩을 앵커로 참조한다(`](#주요-오픈소스-관리-도구-소개)`). 헤딩을 고치면 그것을 가리키는 모든 링크가 죽는다. 헤딩을 바꿔야 하면 **그 헤딩을 가리키는 링크를 전부 함께 고친다.**
   ```bash
   grep -rn "](#고칠-헤딩-슬러그)" content/en/
   ```
2. **이미지는 페이지 번들 안에 두고 확장자 없이 참조한다.** `static/` 디렉토리가 없으므로 루트 `images/`에 넣은 파일은 배포되지 않는다. 이미지는 `content/en/{section}/` 안에 있어야 한다.
3. **각주는 사용처와 정의가 짝을 이룬다.** 정의 없는 각주는 본문에 `[^label]`이 그대로 노출된다.

## Hugo / Docsy 마크업

### 이미지 + 캡션

```markdown
{{< imgproc compliance-process-2026 Fit "768x768" >}}
<center><i>[오픈소스 컴플라이언스 프로세스]</i><center>
{{< /imgproc >}}
```

- 파일명은 **확장자 없이** 쓴다. 실제 파일은 `content/en/{section}/compliance-process-2026.png`.
- 크기 지시는 기존 원고 관례를 따른다 — 도해 `Fit "768x768"`, 로고 `Fit "384x384"`, 넓은 표·화면 캡처 `Fit "1024x768"`.
- 캡션은 `[제목]` 형태로 대괄호를 포함한다. 출처가 있으면 `<center>기관명, 문서명 : URL</center>`로 별도 줄에 쓴다.
- 이 마크업이 동작하는 것은 `markup.goldmark.renderer.unsafe = true` 설정 때문이다. raw HTML을 쓸 수 있으므로 `<center>`, `<sub>`, `<br>`가 허용된다.

### 알림 박스

```markdown
{{% alert color="success" %}}
본 장에서는 일반적으로 발생할 수 있는 과정을 서술한다. 특정 기업의 예외 사항을 모두 다루지 않으니 유의한다.
{{% /alert %}}
```

`{{%` 는 내부 마크다운을 렌더링하고 `{{<` 는 렌더링하지 않는다. alert/pageinfo는 `{{%`, imgproc는 `{{<`를 쓴다. 사용 가능한 shortcode는 Docsy 제공분(`alert`, `pageinfo`, `imgproc`, `blocks`, `readfile`, `swaggerui`)뿐이다 — 없는 shortcode를 쓰면 빌드가 실패한다.

### 각주

```markdown
2026년 기준 감사된 코드베이스의 절반 이상이 라이선스 충돌을 포함한다[^ossra2026].

[^ossra2026]: Open Source Security and Risk Analysis 2026 : https://example.org/report
```

정의는 **해당 문단 직후**에 둔다. 파일 끝에 몰아 쓰지 않는다 — 개정 시 문단을 옮기면 각주 정의를 함께 옮겨야 하므로 근접 배치가 유지보수에 유리하다. 라벨은 소문자·하이픈·숫자만 쓴다.

### 헤딩 계층

`##`(대주제) → `###`(절) → `####`(항) → `#####`(단계·세부). `#####`는 기존 관례상 굵게 쓴다.

```markdown
##### **1. 오픈소스 라이브러리 식별**
```

`#` 단독 헤딩은 쓰지 않는다 — front matter의 `title`이 H1이 된다.

### front matter

```yaml
---
title: "오픈소스 사용하기"
linkTitle: "1. 사용하기"
weight: 20
description: >
   
---
```

`weight`가 사이드바 순서를 정한다(intro 10 / using 20 / contributing 30 / releasing 40 / ospo 50). 신규 섹션은 기존 값과 충돌하지 않는 값을 쓴다. `linkTitle`이 사이드바 표기이므로 번호를 붙인다.

### 표

```markdown
| 취약점 심각도 | CVSS 점수 | 대응 시간 |
|---------------|-----------|-----------|
| Critical | 9.0 이상 | 24시간 내 |
```

헤더 열 수와 구분선 열 수가 반드시 일치한다. 표 위에는 무슨 표인지 한 문장으로 안내한다 — 표만 던지면 독자가 무엇을 비교하는지 모른다.

## 문체

'~한다' 평서문 문어체. 상세 규칙은 `references/prose-style.md`에 있으며, 교정 단계에서 그 기준으로 검사된다. 집필 시 최소한 다음을 지킨다.

- 존댓말·구어체·감탄·수사적 질문을 쓰지 않는다.
- 1인칭("우리는")은 쓰지 않는다. 단 "이 가이드에서는"은 관례로 허용된다.
- 영문 약어는 첫 등장에서 한글 표기와 병기한다: `OSPO<sub>Open Source Program Office</sub>`.
- 사실과 필자의 판단을 문장 단위로 분리한다. "A는 B다. 따라서 C가 바람직하다"로 쓰고, "A는 B이므로 C해야 한다"로 뭉치지 않는다.

## 기업 편 / 개발자 편

이 가이드의 핵심 구조다. 각 장은 두 관점으로 나뉜다.

| 구분 | 독자 | 쓰는 것 | 쓰지 않는 것 |
|------|------|--------|-------------|
| **기업 편** | 오픈소스 사무국·정책 수립자 | 정책 항목, 프로세스 단계, 승인 기준, 조직 역할, 도구 도입 판단 | 코드 수준 실행 방법 |
| **개발자 편** | 현업 개발자 | 판단 절차, 확인 항목, 제출 양식, 실제 명령·설정 | 조직 정책 수립 방법 |

같은 주제를 두 편에 중복 서술하지 않는다. 관점을 바꿔 쓴다 — 기업 편이 "라이선스 검토 프로세스를 수립한다"면 개발자 편은 "라이선스 검토를 요청하는 방법"이다.

## 실용 산출물

사용자 요구는 "기업에서 실용적으로 활용 가능한 내용"이다. 개념 설명을 늘리는 개정은 이 요구를 충족하지 않는다. 개정 지시의 `practicality` 필드가 지정한 형태로 만든다.

| 형태 | 언제 | 만드는 방법 |
|------|------|-----------|
| **체크리스트** | 독자가 빠짐없이 확인해야 할 항목이 있을 때 | 마크다운 목록. 각 항목은 확인 가능한 단일 행동으로 |
| **판단 기준표** | 조건에 따라 다른 결정을 해야 할 때 | 표. 왼쪽에 조건, 오른쪽에 판단과 근거 |
| **템플릿** | 독자가 문서를 만들어야 할 때 | 코드 블록 안에 채울 자리를 표시한 양식 |
| **사례** | 추상적 지침을 구체화할 때 | 공개 확인된 기업 사례. 무엇을 참고할지 명시 |

산문으로 풀어 쓰면 지시 위반이다. "다음 항목을 확인한다"고 쓰고 문단으로 나열하는 것은 체크리스트가 아니다.

## 근거 연결

- **지시서의 `evidence`에 연결된 리서치 발견만 근거로 쓴다.** 기억으로 사실을 추가하지 않는다. 이 가이드는 기업의 법적 판단 근거이고, 검증되지 않은 서술은 검증 단계의 비용이 된다.
- 근거가 부족한 자리에는 서술을 만들지 않고 주석을 남긴다:
  ```markdown
  <!-- NEEDS-EVIDENCE: 국내 공공 조달 SBOM 요구 도입 시점 확인 필요 -->
  ```
- 수치는 리서치 결과에서 **전사**한다. 반올림·근사·표현 변경 금지. "53%"를 "절반 이상"으로 바꾸면 검증된 정확한 서술이 부정확해진다.
- `confidence: "low"` 발견은 본문 단정 서술로 쓰지 않는다. 쟁점으로 서술하거나 각주 언급에 그친다.

## 작업 산출 규약

- 초안은 `_workspace/05_draft_{slug}.md`에 쓴다. **`content/en/`을 직접 수정하지 않는다.** 검증 실패 시 롤백을 위한 분리다.
- 초안은 front matter를 포함한 **파일 전문**이다. 변경 부분만 쓰면 다음 단계가 병합해야 한다.
- 한 번에 한 섹션만 쓴다. 다른 섹션을 건드리면 병렬 집필과 충돌한다.

## 안티패턴

- **헤딩 수정 후 앵커 링크 방치** — 링크가 조용히 죽는다.
- **이미지를 루트 `images/`에 배치** — 배포되지 않는다. 페이지 번들 안에 둔다.
- **각주 정의를 파일 끝에 몰아 쓰기** — 문단 이동 시 유실된다.
- **`{{<`와 `{{%` 혼동** — alert 내부 마크다운이 렌더링되지 않거나 imgproc가 깨진다.
- **없는 shortcode 사용** — 빌드 실패.
- **삭제 지시를 무시하고 새 서술만 추가** — 원고 안에서 상충이 발생한다.
- **`practicality`가 지정된 지시를 산문으로 처리** — 실용성 요구 미충족.
- **근거 없는 자리를 그럴듯한 서술로 메우기** — 검증에서 반박되며, 반박을 통과하면 오정보가 출간된다.
