### 근거

24건 중 판단기준표 7건·체크리스트 8건으로, 사내 정책 문안에 그대로 옮길 수 있는 실무 산출물이 절반을 넘는다. 이 산출물들은 '모델을 반입해 → 라이선스를 판정하고 → 대장에 올리고 → 파생물을 배포한다'는 하나의 판단 흐름을 이루므로, 기존 5개 장에 2~5건씩 흩으면 독자가 한 건의 결정을 위해 세 장을 오가야 한다. 대상 자산 자체가 다르다는 점이 결정적이다 — 기존 5개 장은 '오픈소스 소프트웨어 컴포넌트'를 전제로 짜여 있고 이 24건은 모델·데이터셋·AI 생성 코드라는 3개 신규 자산 유형을 다룬다. 분산의 최대 수용처는 using인데 using은 이미 1303행에 발견 84건이 몰려 있어 24건을 더 받을 여력이 없고, 받으면 using이 두 자산군을 동시에 다루는 잡탕 장이 된다. 문서화 시 최소 300행 규모로 현재 최소 장인 ospo(295행)를 넘어 독립 장의 최소 규모를 충족한다. 반대 근거로 research_ai#findings[32]가 'AI 자산은 별도 체계를 새로 만들지 말고 기존 프로세스에 자산 유형으로 추가하라'고 권고하지만, 이는 기업의 운영 체계에 대한 권고이지 문서 구조에 대한 권고가 아니다 — 오히려 이 장의 첫 절(6.1)을 findings[32]로 열어 '기존 프로세스 어디에 무엇을 끼워 넣는가'로 구성하고 각 절에서 기존 장으로 크로스링크를 걸면 권고와 문서 구조가 정확히 일치한다. weight를 60(맨 끝)으로 두는 이유는 기존 5개 장이 '이해→사용→기여→공개→조직'이라는 라이프사이클 순서로 배열되어 있고 AI는 이 순서의 한 단계가 아니라 네 단계를 가로지르는 횡단 주제이기 때문이며, 중간 삽입(예: weight 25)은 기존 장 번호 1~5를 전부 밀어 외부 링크와 기존 독자의 탐색 경로를 깨뜨린다. 이원 구조는 신규 장에도 적용한다 — 기업 편 18건 / 개발자 편 6건으로 비대칭이지만 신규 장만 단일 트랙이면 이 가이드의 골격이 장마다 달라져 독자가 자기 트랙을 잃는다.

### using 비대화 해소

결정: 장 분할은 하지 않는다. 이관 4건 + 중복 병합 1건 + 낡은 서술 삭제 최소 120행 + 목표 분량 상향(1303 → 1620, +317)의 4개 조합으로 감당한다. using 계획자에게 주는 최상위 규칙: 발견 84건은 '순증'이 아니라 '교체'를 기본으로 처리한다. 순증을 허용하는 곳은 research_security#findings[32]가 지정한 신설 소절 5개와 체크리스트·판단기준표뿐이며, 나머지 발견은 기존 서술의 사실 정정·날짜 갱신·표 교체로 반영한다. 발견 1건당 평균 4행을 넘기지 않는다.

- `'오픈소스 보안 관련 규제 및 정책 동향' 절 (content/en/using/_index.md L801-857, 약 57행)` : using → using (SBOM 규제 동향 절 L268-328로 병합, 결과적으로 한 곳에 통합) — research_security#findings[32]가 두 절의 내용이 상당 부분 겹친다고 지적했다. 규제 축 결과를 여기에 흡수해 하나의 '규제 동향' 절로 정리하면 약 40행이 상쇄되고, 독자가 규제 정보를 두 곳에서 찾지 않아도 된다. 병합 위치는 앞쪽(L268-328)으로 하고 뒤쪽은 삭제 후 앵커 링크만 남긴다.
- `'취약점을 보고할 때의 책임 — AI 생성 보고 금지'(curl 사례) 신설 소절` : using (신설 후보였음) → contributing — research_security#findings[32]가 이 소절만 contributing 소속으로 명시했다. 취약점 보고는 외부 프로젝트에 대한 기여 행위이므로 기여 장에 속한다. using 보안 절에는 신설하지 않는다 — using 계획자는 이 주제를 다루지 말고 contributing으로 크로스링크만 건다.
- `using 안의 AI 코딩 도구·AI 모델 라이선스 관련 기존 서술 전부 (있는 경우)` : using → ai (신규 6장) — 신규 6장이 이 주제의 단일 수용처다. using에 남기면 같은 주제가 두 장에 흩어져 독자가 어느 쪽이 최신인지 판단할 수 없다. using에는 1~2행 크로스링크만 남긴다. 예외: 패키지 환각·슬롭스쿼팅(AI가 만든 가짜 의존성)은 공급망 보안 주제이므로 using 보안 절에 신설 유지한다 — research_security#findings[32]의 소절 ⑤.
- `using 안의 조직 차원 정책 수립·검토 조직 구성·전사 거버넌스 체계 서술 (있는 경우)` : using → ospo — ospo는 295행으로 6개 장 중 가장 얇아 수용 여력이 가장 크고, 조직 체계는 원래 ospo의 주제다. using은 '도입·활용의 실무'로 범위를 좁혀야 84건을 감당할 수 있다. 판정 기준: 서술의 주어가 '개발자/프로젝트'면 using에 남기고, '회사/조직/OSPO'면 ospo로 보낸다.
- `using 안의 자사 배포물(제품 출하) 시점 고지·컴플라이언스 산출물 서술 (조건부)` : using → releasing — 조건부 이관이다. using이 '가져다 쓰기'를 다루므로 '내보내기' 시점 의무가 using에 있으면 releasing으로 옮긴다. 다만 제3자 배포 시 고지 의무는 라이선스 준수의 핵심이라 using에서 완전히 빼면 맥락이 끊기므로, 개념은 using에 두고 실행 절차·산출물 템플릿만 releasing으로 옮긴다. using 계획자가 실제 본문을 보고 판단하되, 이관 시 releasing 계획자에게 인계 항목을 명시한다.
